# Прогноз с учётом особых трат — «День за днём»

## Проблема

Линия «Прогноз» в графике «День за днём» (`stats.js`, ~строка 3329) — чистая линейная
экстраполяция `pace = selCum[cD-1] / cD` от текущей кумулятивной суммы. Особые траты
(«особые», `expense.special === true`) не учитываются отдельно:

- если тумблер «особые» выключен — прогноз их вообще не видит;
- если включён — они подмешаны в `selCum` и искажают наклон линии (разовый платёж
  типа аренды тянет линейный темп вверх/вниз вместо того, чтобы остаться разовым
  скачком на своей дате).

В Бюджете уже есть похожая, но агрегатная логика — `_budgetFree()` (budget.js, ~1721):
`specPlan` = минимум суммы особых за 3 прошлых непустых месяца, `reserve =
max(specSpent, specPlan)`, `unpaid = max(0, specPlan − specSpent)` добавляется в
прогноз одним куском. Не различает категории и не размазывает по дням.

## Решение

Новая логика только в `stats.js`, вычисляется рядом с существующим `projLine`
(изменяется сам блок построения `projLine`/`projTotal`, ~3329-3338).
`_budgetFree()` и Бюджет-таб не трогаем.

### 1. Базовый темп — только по неособым тратам

```
regularCum[i]  = кумулятивная сумма НЕ-special трат за дни 1..i текущего месяца
regularPace    = regularCum[cD-1] / cD
```

Экстраполируется линейно вперёд, как раньше — но без подмешивания особых в наклон.

### 2. Прогноз по особым — по категориям

Для каждой категории, у которой есть хотя бы одна `special`-трата в истории:

- `specPlanByCat[catId]` = минимум суммы special-трат этой категории за последние 3
  месяца, где у категории была хотя бы одна special-трата (месяцы без неё пропускаются
  — так же, как в `_budgetFree`, но по каждой категории отдельно, а не суммарно).
- `specSpentByCat[catId]` — сумма special-трат этой категории в текущем месяце.
- `unpaid = max(0, specPlanByCat − specSpentByCat)`.

**Угадывание даты:**
- В каждом историческом месяце берём день месяца самой крупной special-траты этой
  категории (представитель месяца).
- 1 точка данных → используем её день как есть (слабый, но не-нулевой сигнал).
- ≥2 точки, разброс дней ≤3 → `guessDay = медиана дней`.
- ≥2 точки, разброс >3 → гадание не доверяем, fallback.

**Размещение unpaid:**
- `guessDay` определён и строго в будущем (`guessDay > сегодня`, т.е. `≥ cD+1`) →
  весь `unpaid` куском на `guessDay`.
- `guessDay` определён, но сегодня или в прошлом (`guessDay ≤ сегодня`, просрочено
  или совпал с текущим днём) → куском на первый прогнозный день (`cD+1`), а не на
  сам `guessDay` — иначе кусок попадёт в индекс `cD-1`, который тут же затирается
  строкой-якорем факта `projLine[cD - 1] = selCum[cD - 1]`.
- Гадание не удалось → `unpaid` равными долями на каждый из оставшихся дней месяца
  (линейно накапливается до конца месяца).

Вклады всех категорий суммируются в `specialForecast[i]` для `i ≥ cD-1`.

### 3. Итоговая линия

```
projLine[i] = selCum[cD-1] + (regularPace * (i+1-cD)) + specialForecast[i],  i ≥ cD-1
projLine[i] = null,                                                          i < cD-1
```

Не двойного счёта: уже потраченные в этом месяце special-траты — часть факта
(`selCum[cD-1]`), в `specialForecast` попадает только `unpaid`-остаток.

### 4. Тумблер «особые вкл/выкл»

Прогноз следует тумблеру (как и факт/среднее сейчас):
- **выкл** → прогноз = шаг 1 (только regularPace), шаг 2/3 не применяются, `specialForecast = 0`.
- **вкл** → полная логика (шаги 1-3).

### Границы применимости

Условие построения прогноза не меняется: только текущий месяц, режим «весь месяц»,
`selCum[cD-1] > 0`, `cD < daysInSel` (как сейчас, ~3332).

### Известное ограничение

Если состав/суммы special-трат категории не повторяются из месяца в месяц (не
рекуррентные), угадывание даты и пропорциональное размазывание — грубое приближение.
Это ожидаемо и соответствует запросу («хотя бы пропорционально, если точно нельзя»).

## Не в скоупе

- Бюджет-таб (`_budgetFree`, `oblRow`) — остаётся агрегатным, без деления по категориям.
- Планирование/расписание будущих special-трат вручную — не добавляется, только
  прогноз на основе истории.

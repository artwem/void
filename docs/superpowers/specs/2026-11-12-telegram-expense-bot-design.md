# Расходы одной кнопкой через Telegram-бота

## Замысел и зачем

У пользователя уже есть личный Main Mini App `@voiddmv_bot`, полная PWA и синхронизация через Apps Script. Теперь частые расходы должны добавляться прямо из чата бота без открытия приложения: под полем ввода постоянно видны кнопки шаблонов с готовыми суммами, и одно нажатие сразу создаёт расход в V.O.I.D. на всех устройствах.

Основной сценарий выбран пользователем: **постоянная клавиатура без команды `/add`, один тап сразу сохраняет расход**. Подтверждать сумму перед каждой записью не нужно. Для защиты от случайного нажатия после успешной записи бот показывает кнопку «Отменить».

## Цели

- Использовать существующие `DB.templates` как единственный источник названий, сумм, категорий, комментариев и признака разовости.
- Показывать актуальные активные шаблоны из последней версии `nto_data.json` на Drive постоянной `ReplyKeyboardMarkup` под полем ввода.
- По одному нажатию создавать расход на текущую дату в часовом поясе пользователя и только после успешной записи сообщать об успехе.
- Давать возможность отменить только что созданную запись; отмена должна синхронизироваться как обычное мягкое удаление.
- Сохранить совместимость с текущей PWA, Mini App, `budgetDB_v2`, `buildPayload()` и циклом pull → merge → push.
- Не потерять расход бота при параллельной отправке клиентом более старой копии базы.
- Ограничить использование бота одним Telegram user ID и не хранить секреты в репозитории.

## Не входит и анти-цели

- Нет произвольного ввода суммы, категории, комментария или даты текстом в первой версии.
- Нет создания и редактирования шаблонов через бота; это по-прежнему делается в приложении.
- Нет публичного доступа, групп, нескольких пользователей и общих чатов.
- Нет Bot API backend вне Apps Script, нового сервера, базы данных или npm-зависимости.
- Нет замены Mini App: существующий полный интерфейс остаётся без изменений.
- Не должно получиться, что бот сообщает об успехе до записи на Drive, повторная доставка сообщения или callback Telegram создаёт дубль, чужой пользователь видит шаблоны или старая PWA затирает новую запись бота.

## Выбранный подход и альтернативы

### Apps Script + Telegram webhook — выбрано

Расширить существующий `apps-script/Code.gs`. Он продолжает обслуживать текущие действия `ping`, `pull`, `push`, `listBackups`, `readBackup`, а запросы Telegram обрабатывает отдельной веткой того же `doPost`.

Плюсы: один уже настроенный хостинг, прямой доступ к `nto_data.json`, нет новых runtime-зависимостей. Цена: необходимо обновить развёртывание Apps Script, задать Script Properties и один раз зарегистрировать webhook.

### Отдельный backend — отклонено

Cloudflare Worker или сервер отделил бы Telegram от Drive API, но добавил бы второй деплой, новые секреты и интеграционный код без пользы для личного сценария.

### Кнопки-ссылки в Mini App — отклонено

Deep link с заполненной формой не требует backend, но пользователь выбрал сохранение одним нажатием без открытия приложения.

## Пользовательский сценарий

1. Один раз пользователь запускает бота командой `/start`: это техническое требование Telegram перед первым ответом бота. Бот читает свежую базу с Drive и отвечает постоянной `ReplyKeyboardMarkup` с `resize_keyboard: true`, `is_persistent: true` и активными шаблонами в их текущем порядке.
2. Кнопки остаются под полем ввода без команды `/add`. На каждой видны название и сумма. Нажатие отправляет боту текст кнопки как обычное сообщение.
3. Бот принимает только текст, точно соответствующий кнопке актуального шаблона, создаёт расход на сегодня и отвечает только после успешной записи. Ответ содержит свежую клавиатуру, поэтому она обновляется при следующем обращении.
4. Отдельным сообщением бот подтверждает название и сумму и показывает inline-кнопку «Отменить». Постоянная клавиатура остаётся доступной для следующей записи.
5. После «Отменить» расход помечается удалённым, а сообщение подтверждения обновляется и теряет кнопку отмены.
6. Обычная синхронизация PWA/Mini App забирает запись или её удаление при следующем pull. Немедленно открытое приложение обновляется через существующий `syncCycle()`, нового push-канала не появляется.

Неизвестный текст не создаёт расход: бот отвечает подсказкой и свежей клавиатурой. Если активных шаблонов нет, бот предлагает создать их в приложении. Изменения шаблонов становятся видны боту после синхронизации приложения с Drive; несохранённые локальные изменения он не видит. Telegram не позволяет заменить клавиатуру мгновенно без действия пользователя.

Кнопки располагаются по две в ряд. Если шаблонов больше десяти, служебные кнопки «Ещё» и «Назад» переключают страницы клавиатуры без создания расхода. Ограничение 64 байт на `callback_data` относится только к inline-кнопке отмены.

## Запись и совместимость данных

Новый расход повторяет `addFromTemplate()`:

- новый уникальный `id` и `updatedAt: Date.now()`;
- дата через `Utilities.formatDate()` в `Session.getScriptTimeZone()`, для установки используется `Europe/Moscow`;
- `cat` и авторитетный `catId` из шаблона/текущего `catIds`, без переназначения «сирот»;
- сумма без округления до рубля;
- комментарий `name + ': ' + comment`, если комментарий есть, иначе `name`;
- `oneoff: true` для разового шаблона, включая legacy `special`, иначе `null`;
- дополнительное служебное поле `source: 'telegram'`, которое сохраняется при клиентских правках и нужно для защиты от гонок.

При отмене запись с тем же `id` получает `_deleted: true`, `amount: 0` и новый `updatedAt`. Отменять через бота можно только записи с `source: 'telegram'`; чужие расходы callback изменить не может.

Схема `budgetDB_v2`, клиентские миграции, `buildPayload()` и правила LWW не меняются. Неизвестное ранее поле `source` остаётся внутри обычной записи расхода и переносится существующим payload.

## Гонки и целостность Drive

Запись бота выполняет read-modify-write последней версии `nto_data.json` под тем же `LockService`, что обычный push, включая суточное резервное копирование перед перезаписью.

Одной блокировки недостаточно: клиент мог сделать pull до записи бота, а push — после неё. Поэтому обычный **не-force** `saveData(content)` перед записью дополнительно объединяет входящий payload с записями `source: 'telegram'` из текущей Drive-версии по `id` и `updatedAt`:

- отсутствующая в старом payload запись бота добавляется;
- более новая клиентская правка или tombstone побеждает;
- более новая запись/отмена бота побеждает;
- одинаковый `id` не дублируется.

Это узкий server-side merge только для записей бота, а не второй общий алгоритм синхронизации. Force-push при восстановлении резервной копии сохраняет прежнюю осмысленную семантику полной замены и не подмешивает старые записи бота.

## Идемпотентность Telegram

Telegram может повторить доставку сообщения и callback. Под `LockService` обработчик проверяет ключ `message:<chat_id>:<message_id>` для постоянной клавиатуры или `callback:<callback_query.id>` для отмены в `CacheService` и `PropertiesService`. После успешной записи ключ сохраняется в Cache на 600 секунд и в Properties на 24 часа; устаревшие ключи очищаются. Ошибка не оставляет done-маркера и допускает повторную обработку. Повтор той же доставки не создаёт второй расход и не меняет запись повторно. Два осознанных нажатия имеют разные `message_id` и создают разные расходы.

Ответ `answerCallbackQuery` обязателен как при успехе, так и при ошибке отмены. Ошибка чтения, блокировки или записи возвращает пользователю просьбу повторить позже и никогда не отображается как успешное сохранение.

## Безопасность

- В Script Properties задаются `TELEGRAM_BOT_TOKEN`, `TELEGRAM_ALLOWED_USER_ID`, `TELEGRAM_WEBHOOK_SECRET`.
- Токен бота не попадает в `Code.gs`, репозиторий, клиентский payload, логи, скриншоты или тестовые фикстуры.
- Webhook регистрируется на `/exec`-URL с секретным query-параметром; обработчик проверяет его до любой работы с Drive. На отсутствие доступа к HTTP-заголовкам Apps Script не полагаемся.
- Сообщения и callbacks принимаются только из личного чата и только от разрешённого Telegram user ID. Остальные получают отказ без шаблонов и финансовых данных.
- Существующий `SECRET` синхронизации продолжает защищать прежние действия API независимо от webhook.
- `readBackup` и остальные существующие защиты не ослабляются.

## Настройка и выпуск

- В Apps Script добавляется одноразовая функция регистрации webhook через Bot API `setWebhook`; URL берётся из `ScriptApp.getService().getUrl()`. Токен используется только внутри UrlFetch-запроса и не печатается.
- Предусматривается функция отключения webhook для отката.
- Часовой пояс проекта Apps Script — `Europe/Moscow`.
- Ожидаемая версия Apps Script повышается до `11.0`, видимая версия клиента — до `v1.90.0`; `APPS_SCRIPT_VERSION`, `sw.js` и CSS query обновляются синхронно.
- Старые клиенты сохраняют прежний pull/push API. Настройка Mini App в BotFather повторно не требуется.

## Проверка и приёмка

Автоматические проверки существующего раннера остаются зелёными. Для серверной логики добавляются проверки чистых функций и сценариев с mock Drive/Telegram: выбор активных шаблонов в постоянной клавиатуре, соответствие записи `addFromTemplate()`, запрет чужого пользователя, повтор сообщения и callback, навигация без создания расхода, отмена, ошибка записи, отсутствие дублей и гонка «старый клиентский push после записи бота». Отдельно проверяется, что force-restore не смешивается с более новыми bot-записями.

После публикации вручную на реальном Telegram:

1. Настроить Script Properties и webhook, один раз выполнить `/start` и проверить постоянные кнопки только у разрешённого пользователя.
2. Создать расход каждого типа шаблона, проверить сумму, категорию, комментарий, дату и разовость в PWA/Mini App.
3. Проверить две осознанные записи подряд и отсутствие дубля при повторной обработке сообщения/callback.
4. Отменить тестовую запись и убедиться в синхронизации удаления.
5. Проверить гонку с открытой PWA, обновление шаблона после синка и отказ постороннему Telegram-аккаунту.
6. Удалить тестовые расходы и убедиться, что реальные данные не изменились.

## Решения, оставленные реализации

- Точное разбиение функций внутри `Code.gs` и названия защищённых внутренних хелперов.
- Способ генерации уникального ID в Apps Script с сохранением строкового формата существующих записей.
- Компактная разметка пагинации и текст сообщений без изменения выбранного сценария.
- Техника Node-проверок Apps Script с подменой внешних сервисов без второго production-харнесса.
